# Comparable observation history: storage audit and proposed evidence contract

Research dated 2026-10-27 for [What observations can support comparable price history?](tickets/observation-history.md). This is a proposed planning decision for parent review. The ticket, map and index are unchanged.

## Finding and decision proposed

The current application does **not establish an auditable comparable-price time series**. It replaces the latest per-watch listing snapshot, persists selected change events, and exposes an unwritten `price_history` table through API, CLI and chart readers. Neither an existing table nor event receipts demonstrate longitudinal coverage. A separate HotUKDeals cache and a CamelCamelCamel summary path do exist, but neither is a qualified merchant-observation archive.

Reuse SQLite, existing connectors, watch execution, scheduler and health machinery. The smallest sufficient extension is a durable per-source acquisition outcome plus versioned observation evidence and comparison qualification at the existing executor/storage boundary. Retain observations independently of alert changes and presentation filters. Make history readers consume qualified, explicitly segmented evidence. Adding an INSERT to today's narrow history table alone cannot supply missing identity, context, provenance or coverage.

No existing retained watch data is accepted here as a repeated comparable UK delivered-price series. Future collection begins only for individually permitted routes and qualified subjects. Until then, show dated leads and limited evidence; withhold usual-price savings, category averages, market-wide historical lows and continuous availability claims.

## Actual storage writers and readers

### Current listing snapshot

**S:** Schema identifies `listings` as current state, unique by `(watch_id, source, source_listing_id)` with columns plus a serialized listing ([schema.py:197–214](../../../src/pricerecon/db/schema.py)). `get_previous_listings` reads that state; `store_listings` deletes every listing for the watch, inserts the received list and commits ([diff_engine.py:48–78,202–237](../../../src/pricerecon/core/diff_engine.py)). `run_check` computes a diff and replaces state before storing events, in separate transactions ([diff_engine.py:329–358](../../../src/pricerecon/core/diff_engine.py)). Snapshot success followed by event-write failure therefore has no atomic snapshot/event receipt; concurrent runs are not made serializable by this function.

Readers are the next diff, first-run check, listings API, executor results and export ([diff_engine.py:81–87,103–109](../../../src/pricerecon/core/diff_engine.py); [api/listings.py:49–84](../../../src/pricerecon/api/listings.py); [watch_executor.py:659–687](../../../src/pricerecon/core/watch_executor.py); [api/export.py:95–115](../../../src/pricerecon/api/export.py)). Exported listings omit `listing_json`, and the listing export branch does not run when `watch_id` is supplied. This export is not a lossless evidence backup.

### Diff events, notifications and derived signals

**S:** `compute_diff` detects new listings, decreases, increases, stock transitions and absence. It compares price numerically without checking currency, identity/configuration, destination, eligibility or cost basis. It converts event comparison amounts to floats; stock events require both booleans to be known. Current duplicates collapse by source/ID with last entry winning in the diff map ([diff_engine.py:103–191](../../../src/pricerecon/core/diff_engine.py)). The snapshot insertion still iterates the original list, so identical keys can violate the SQL uniqueness constraint rather than being resolved consistently.

`store_events` writes **new listings, price decreases, stock changes and listings gone**, but has **no price-increase loop** ([diff_engine.py:240–326](../../../src/pricerecon/core/diff_engine.py)). First-run detection is simply an empty prior snapshot, and all initial events are suppressed. An empty-result run can empty that snapshot and make a later recovery look like another silent first run ([diff_engine.py:81–87,347–356](../../../src/pricerecon/core/diff_engine.py)). Unchanged observations produce no events. Listing-gone payloads contain locator/title/URL, not the last price and complete evidence. No change-event sequence can reconstruct all sampled prices, observation opportunities, first capture, offer availability or the duration of an unchanged price.

Readers: per-watch/all-event APIs paginate events ([api/events.py:61–136](../../../src/pricerecon/api/events.py)); executor `get_watch_events` returns decoded event JSON ([watch_executor.py:690–716](../../../src/pricerecon/core/watch_executor.py)); frontend EventLog fetches that API ([EventLog.tsx:31–48](../../../frontend/src/components/EventLog.tsx)). Export omits event JSON ([api/export.py:144–167](../../../src/pricerecon/api/export.py)). `/signals` derives from `events`, not `deal_signals`; its drop parser expects `old_price`/`new_price`, whereas the diff emits `previous_price`/`current_price` ([api/signals.py:88–145](../../../src/pricerecon/api/signals.py); [diff_engine.py:134–142](../../../src/pricerecon/core/diff_engine.py)). It is not an independent price source.

Notifications append event/channel/status/message/error records ([notifications.py:330–354](../../../src/pricerecon/core/notifications.py)). These are delivery logs, not independent merchant observations. No notification timestamp establishes when a source price became available.

### Failure, filtering, clocks and deletion gaps

**S:** Disabled/unknown sources and fresh authentication failures are skipped; exceptions update health and continue. Only successful returned listings join the common list, which is filtered and handed wholesale to `run_check` ([watch_executor.py:320–341,465–547](../../../src/pricerecon/core/watch_executor.py)). The diff has no per-source result/completeness parameter. Thus failed, skipped, capped, changed-query or filtered-out results can produce the same absence event as a genuinely missing offer. A connector returning cached or swallowed-error `[]` may even be marked `ok` by this boundary ([watch_executor.py:471–485](../../../src/pricerecon/core/watch_executor.py)). `ok` means the call returned, not complete catalogue or exact-offer success.

Optional deduplication removes condition suffixes and keeps the first matching title, without source/seller/configuration in its key ([watch_executor.py:280–293](../../../src/pricerecon/core/watch_executor.py)). Alert/preference filtering before retention means later filters can change observed membership. This cannot establish merchant disappearance or independent seller/time diversity.

`NormalizedListing.timestamp_seen` defaults to naive `datetime.utcnow`; replacement storage uses that if present, otherwise aware UTC now. History/event defaults are insertion clocks. `last_check_at` is updated by the scheduler callback **before** executing and again after executor diff, so it is not proof of a successful qualified capture ([models/listings.py:57–85](../../../src/pricerecon/models/listings.py); [diff_engine.py:227–232](../../../src/pricerecon/core/diff_engine.py); [schema.py:225,240](../../../src/pricerecon/db/schema.py); [app.py:66–93](../../../src/pricerecon/app.py); [watch_executor.py:549–556](../../../src/pricerecon/core/watch_executor.py)). Preserve original precision/zone and distinguish capture, source publication and persistence time.

Watch deletion issues `DELETE FROM watches` ([api/watches.py:309–319](../../../src/pricerecon/api/watches.py)); schema declares child cascades, but searched connection paths do not enable `PRAGMA foreign_keys`. **D:** SQLite documents enforcement as connection-specific and normally disabled by default; therefore cascade declarations alone cannot certify effective cleanup. No runtime pragma or compile option was inspected. [SQLite foreign-key documentation, §2](https://www.sqlite.org/foreignkeys.html). No age-based history/event purge or backup-expiry implementation was found in inspected application source. The HUKD cache pruning above is a separate, incomplete rule.

## Proposed comparable observation evidence

**P:** Store the source assertion even when comparison is unresolved, where permitted; qualify it for a specific metric/cohort separately. “Item-price comparable,” “UK delivered-total comparable” and “conditional personal scenario” require different cost/eligibility gates. Unknown is explicit, with a reason and affected claim; it is never zero, false, NEW, GBP or a wildcard.

Each durable observation must reference:

| Evidence group | Minimum retained content and comparison rule |
| --- | --- |
| Subject and identity | Observation ID; category; exact configuration ID and identity-policy/mapping version; product-kind gate; mandatory dimension claims and evidence references. Namespaced source, merchant/storefront, listing, selected variation/SKU and seller identity where necessary. Preserve opaque IDs, original options and purchase mode. No family/PID/title-only promotion. |
| Condition and unit | Raw provider condition ID/label/descriptors and versioned category condition cohort; new/used/refurbished, cosmetic/functional limits, included components; item quantity, pack count, unit and bundle. One used unique item is a distinct offer; another relisting/seller needs an explicit relation, not identity by title. |
| Purchase context | Destination country and required region/postcode scope (minimise private data); fulfilment origin if relevant; quantity; shipping option; buyer/public eligibility, membership, new-customer, account, payment, minimum spend and coupon applicability. Unknown applicability remains unqualified. Do not retain session secrets. |
| Monetary evidence | Exact decimal amount and original currency; item versus subtotal versus full delivered amount; shipping, VAT inclusion, import/duty/carrier/payment components and known/unknown/not-applicable state. Public/no-code and each compatible discount scenario stay separate. FX source, quote/base, rate, timestamp, rounding and conversion version, if used. Preserve original monetary value; do not compare item price against delivered price or nominal cross-currency numbers. Final UK arithmetic belongs to the UK-cost decision. |
| Availability | Selected-offer buyability, stock/quantity claim and observed scope; in-stock, out-of-stock, preorder, supplier/orderable, ended and unknown separated. Generic Product InStock cannot qualify a selected SKU. A successful fetch with no qualified offer is a coverage outcome, not zero price. |
| Clocks | Acquisition attempt start/end, actual capture time with zone/precision; source-reported publication/price-effective time where supplied; first/last seen derived from captures; ingestion time; freshness assessment as of a stated clock. Record unknown precision and source clock uncertainty. Never backdate capture to a seller's post date. |
| Provenance and replay | Route/method, URL and relevant nonsecret request context, run/attempt ID, bounded page/cursor scope, issuer and original claim lineage; connector/parser/schema versions; permitted evidence excerpt/pointer and integrity hash; whether direct capture, cache replay, imported source sample, extracted assertion or human correction. Hash proves identity, not truth or rights. |
| Qualification and rights | Per-metric state/reasons, conflicts, policy and cost/discount versions; supersession/correction links; source-specific permitted purpose, retention deadline and display/derivation limits with evidence. An excluded observation remains out of every dependent definitive result. |

This implements the separation already required by [identity-evidence-research.md:5–9,62–80,99–109](identity-evidence-research.md). The current transport supports some optional fields, but `total_landed_cost` is explicitly only “price + shipping,” and the model has no required capture lineage/destination/eligibility contract ([models/listings.py:50–103](../../../src/pricerecon/models/listings.py)). Do not infer that serialized optional fields meet this proposed contract.

Comparable series identity is a versioned tuple of configuration, condition cohort, quantity/bundle, destination scope, currency/conversion basis, cost metric, eligibility scenario and purchase mode. Offer identity additionally names merchant/seller/listing/variation. Cross-seller cohort analysis may use multiple offers only after cohort qualification; it must preserve seller and time coverage rather than erase it into one price line.

## Proposed correction, duplication and lifecycle rules

1. **Acquisition idempotency:** persist one observation for an actual capture/context/offer; retries of persistence use its stable acquisition/observation ID. Two routes quoting the same merchant capture, two watch matches, a translated URL, affiliate URL, community repost, cached replay or CSV re-export are linked lineage, not independent observations. Separate source namespaces/storefronts; use tuples, not an ambiguously parsed pipe string (eBay IDs themselves contain pipes). Conflicting duplicates are retained as conflicts, not first/last-wins price selection.
2. **Repeated unchanged captures:** a genuinely new permitted merchant fetch at a new time is a new sampling opportunity even if value is unchanged. It adds temporal evidence, not independent seller corroboration. Keep sample/run IDs even if identical permitted payload bytes are stored once. Within-period weighting, seller/time diversity and baseline sufficiency remain for baseline policy; rapid retries must not inflate counts.
3. **Corrections:** append a version with actor, recorded time, corrected assertion/mapping, reason, supporting evidence, scope and effective-time interpretation. Keep original evidence as permitted. Distinguish parser repair, seller revision, identity remap, cost/FX recalculation and user-preference change. A current page cannot retrospectively prove a past option. A newly discovered capture can describe the past with its real capture time and later ingestion time; it does not fill all intervening periods.
4. **Invalidation:** wrong SKU/condition/destination/currency/cost basis excludes affected observations from the intended cohort; retain under a different supported subject only if evidence warrants it. Invalidate derived lows, baselines, rankings and alerts by dependency IDs/policy versions, then recompute. Preserve the fact and basis of prior notifications; correction-notification behavior belongs to experience policy. If deletion removes mandatory support, mark downstream outputs unsupported and remove prohibited derivatives rather than preserving an unjustified numeric claim.
5. **Failed/skipped/partial sources:** record each attempt as success-complete-for-declared-scope, success-partial/capped, blocked, failed, skipped, cached fallback or parsing/qualification failure, including query/filter/version and affected scope. Preserve last successful observation with its real age; do not update its capture clock or infer gone. A complete search result means complete only within the declared scope, not the merchant catalogue.
6. **Disappearance:** not returned from search means `not observed in this scope`. Changed ranking, paging cap, query, filters, authentication and parser changes are alternative causes. A successful exact-offer check explicitly reporting ended/unavailable may establish that state at that time; a 404 alone needs route/ID validity and error classification. Repeated complete scoped absences can support a policy-labelled stale/not-seen state, never prove sold or continuous out-of-stock. No arbitrary number of missed checks establishes sale. Reappearance starts a new capture under the same supported identity or a distinct offer if identity changed; it is not a new cold start that erases prior gaps.
7. **Freshness and gaps:** current display eligibility expires by route/use policy; historical validity is assessed at original capture and can remain if rights and evidence allow. Expired current stock is unknown now, not historically false. Preserve outage intervals, source onboarding dates, skipped schedules, exclusions and unknown coverage. No interpolation, forward-filled price, zero-valued gap or continuous-availability line is an observed fact. Exact state transition time is unknown between samples unless source evidence supplies it.
8. **Retention:** “append-only” is an audit behavior within permission, not a mandate to retain forever. Minimise raw content and private fields; track source-specific deadlines and deletion/revocation conditions across excerpts, observations, imports, exports, caches, backups and derived outputs. A hash or derived minimum is not an automatic exemption. Keep a noncontent tombstone/reason only where permitted. No global 7/30/90-day archive duration is justified here.

## Smallest change boundary and acquisition plan

**P:** No implementation or migration is proposed for execution in this task. A future bounded change should:

1. Extend the existing connector→executor result boundary with a per-attempt outcome and declared scope/completeness, including cached replay and source/query/filter identity. Preserve existing connectors and scheduler; do not create a second collector or generic event platform.
2. Introduce a versioned observation envelope and qualification result alongside `NormalizedListing`. Persist necessary permitted assertions **before presentation/alert deduplication**, with excluded/unknown reasons; qualify costs and discounts through their downstream contracts. This means preserve relevant evidence, not retain every raw page indiscriminately.
3. Use the existing SQLite persistence owner for attempts, observations and correction dependencies, linking watch membership separately from observation identity. Define uniqueness/idempotency and a transaction or explicit recoverable commit-state boundary for attempt/observations/current projection/events. The present history table cannot remain the sole source of truth without extension; choose exact additive tables/columns only after a separately authorised inventory of actual deployed schema/rows and retention requirements. Do not backfill from events by pretending they are samples.
4. Keep current-listing and notification behavior as compatibility surfaces, but make disappearance source-aware. History API/export/chart must preserve qualified series IDs, currency/cost labels, full timestamps, gaps, versions, provenance and pagination. A flattened mixed line must not become the product's evidence claim.
5. Add rights-driven expiry/invalidation within this same storage boundary and existing scheduling substrate where appropriate. No new scheduler/queue/service is justified by this investigation.

Future staged acquisition, with explicit stops:

- **Stage 0 — inventory and permission:** under separate authority, inspect deployed schema/version, counts and capture ranges without starting application initialization; locate any external writers, exports and cache/backups. Inventory existing native access/plan first. Reconcile retained corpus hashes/lineage and grant before importing. This research intentionally performed none of those runtime/DB steps.
- **Stage 1 — closed fixture proof:** demonstrate duplicate watch membership, identical repeated values at different capture times, conflicting duplicates, GBP→USD, wrong SKU correction, quantity/condition changes, timestamp precision, cache replay, failures/partial pages, filter/query changes, retention deletion, transaction interruption and reappearance. Exercise all event classes including increases, first capture and recovery after zero results. These are future acceptance cases, not tests claimed run.
- **Stage 2 — bounded source qualification:** only permission-cleared routes, declared query/page limits and stable exact subjects; measure actual capture completeness, fields and failures. Start with AliExpress/eBay review lanes and the independent San Martin contrast only after their respective retention/identity gates pass. Do not assume these provisional lanes are ready for a longitudinal pilot. Keep blocked manufacturer, UK, international, used and community routes visible in coverage.
- **Stage 3 — prospective sampling:** reuse existing scheduler only after cadence/budget approval in operating-envelope work. Record every due/attempted/missed opportunity and changed query scope. Cover ordinary periods and promotions, new/used cohorts and merchant diversity; a one-day burst cannot establish normal sale cycles. No fixed collection duration, sample-count sufficiency or baseline formula is selected before the baseline-policy investigation evaluates evidence.
- **Stage 4 — empirical review:** report eligible observation count, distinct capture periods and sellers, actual span, exclusion reasons, gaps, censored beginning/end and rights-limited deletions. Assess stable-price duration only as sampled evidence. Decide whether candidate baseline windows are supportable using real permitted data, not an assumed calendar wait.

Cold start is per configuration/cohort/metric/source coverage, not merely a watch having rows. The first qualified capture is one dated price with no usual price or savings percentage. New discoveries start then; category discovery must not require the product to have been individually tracked already. Historical imports may extend that specific series only when dated original samples, context, provenance and rights qualify. Keep imported and direct-sampled origin labels and coverage separate; importing today does not create a second independent confirmation of yesterday.

Missing periods remain missing, including all periods before onboarding, collection outages, partial/capped results and periods purged under terms. After resumption, show a new point and gap, not an invented connecting run of prices. Offline correction can change qualification of existing evidence, but cannot acquire absent historical availability/cost. If rights prevent the evidence duration needed for a baseline, defer that baseline or seek a permitted alternate source; do not silently shorten the evidence bar.

**Supportable now:** the inspected source gaps; existence of dated bounded access/selection receipts; retained-manifest record counts and identity conflicts with their provenance labels. A report can say a specific price was displayed in a dated receipt if it carries that receipt's unresolved context; it cannot label it an exact comparable obtainable UK total.

**Supportable after future evidence gates:** “lowest qualifying retained observation in this stated window and checked coverage,” with capture date, metric, currency, eligibility, exclusions, gaps and policy version; a sampled price change between two equivalent contexts; current comparable offer within checked coverage when current freshness/availability and cost gates pass. A minimum of one eligible point is merely that point and must carry insufficient-history wording; it is not a meaningful usual-price baseline.

**Withheld:** historical/all-time/global low; category market minimum or average without coverage/permission; usual obtainable price or fabricated savings from first snapshots, struck-through prices or imported summary minima; completed sale prices inferred from asking prices/Best Offer/auction bids; continuous stock/sale duration between samples; sold/disappeared inferred from failed/search-capped sources; UK delivered totals with unknown costs; independence inferred from multiple leads/exports/watch matches; present availability inferred from old cached evidence. Baseline-policy, UK-cost, public-discount and operating-envelope decisions remain separate gates.
