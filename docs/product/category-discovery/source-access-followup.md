## Correction to the access interpretation

A `/search` disallow is a path restriction, not proof that `/products/...`, a clean category URL or the entire host is inaccessible. Evaluate the actual request URL against the applicable user-agent group, plus the source's separate access guidance and terms. Do not identify a user-initiated browser as GPTBot merely because an OpenAI model is operating it; conversely, do not choose a misleading identity to evade a restriction. Robots crawlability does not grant storage, republication, image reuse or historical-database rights.

## Militado: an explicit public-HTML route, with identification prerequisite

Current [robots.txt](https://www.militadowatch.com/robots.txt) and [agents.md](https://www.militadowatch.com/agents.md) were fetched through an ordinary documentation GET, both HTTP 200. The agent guidance expressly permits read-only public HTML for context, including `/products/{handle}`, `/collections/all`, `/collections/{handle}` and discovery through `/sitemap.xml`, **subject to its agent-identification requirement**. It prefers structured shopping tools, requires WebMCP for agent shopping actions, and says server-to-server and hosted/remote browser traffic must use Web Bot Auth. It specifies respecting 429/Retry-After. These statements do not authorise this task to install Shop, link an account, use checkout or perform cart actions.

Candidate next URLs, once compliant identification is established: [sitemap](https://www.militadowatch.com/sitemap.xml), [all collection](https://www.militadowatch.com/collections/all), then a real ML05/ML05B product URL discovered there. No product handle was guessed. Avoid collection sorting/multiple-filter traps, private/transactional routes and AJAX/cart surfaces disallowed in its robots file. No published maximum read-only page budget was found; retain the user's bounded session budget rather than infer unlimited crawling.

[Shopify's current Web Bot Auth section](https://shopify.dev/docs/api/storefront/latest#identifying-bots-with-web-bot-auth) describes signed requests for bot operators and higher limits; this generic platform guidance is less strict in wording than Militado's store-specific requirement. It does not erase that requirement. The signing background it links is [Cloudflare's implementation guide](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/); that guide was not independently inspected in this bounded pass.

Unanswered prerequisites: Does T3 preview or the existing Byparr deployment sign outbound requests with Web Bot Auth? What operator identity/key directory is used? Does a signature survive browser navigation/subrequests and redirects? What source authentication, if any, does the chosen read-only integration require? A User-Agent string, successful HTML response or solver success does not demonstrate signing. No signature, key, account or authentication change was attempted. Hosted Proxmox/Byparr browsing fits the guidance's remote/server traffic description; it cannot be treated as a local human browser exemption.

## Recommended next use

Militado has the clearest explicit read-only HTML path but needs verifiable agent identification. For other merchants, use a small clean category/detail route only after confirming the actual rules and remaining terms constraints; preserve search-lane failures as failures of that lane. Successful retrieval alone does not settle collection permission, selected configuration, UK destination or retention. This follow-up changes no ticket status and qualifies no offer or recurring monitoring route.
