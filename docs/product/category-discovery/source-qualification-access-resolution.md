## What changed

**Cloudflare enrollment is not a prerequisite for Shopify Web Bot Auth.** Shopify explicitly says its link to Cloudflare's signing guide is background and enrollment in a Cloudflare program is unnecessary. Therefore installing a Cloudflare solver, registering a Cloudflare verified bot, or changing browser fingerprints is not the missing Shopify identity solution. The remaining work is a real signing identity and demonstrated delivery of valid signed requests. [Shopify Storefront API, Web Bot Auth](https://shopify.dev/docs/api/storefront/latest#identifying-bots-with-web-bot-auth).

Militado's agent guidance was freshly fetched with an ordinary documentation GET, HTTP200; its robots file also returned HTTP200. It permits reading public product/collection HTML after identifying agent requests, requires Web Bot Auth for hosted/remote browsers and server traffic, and reserves shopping actions for supported tools. It advertises UCP discovery at `/.well-known/ucp` and MCP at `/api/ucp/mcp`. No catalogue/UCP request or shopping action was made in this documentation pass. Installing Shop or linking purchase history is a recommendation on that page, not a prerequisite for the explicit read-only HTML route. [Militado agent guidance](https://www.militadowatch.com/agents.md), [robots](https://www.militadowatch.com/robots.txt).

## Signing: the smallest concrete route

1. Use an operator identity controlled by this project/operator, with an HTTPS public-key directory and an Ed25519 private key held by its signer. Do not impersonate OpenAI, a human browser or another registered agent. The Cloudflare implementation guide describes the key-directory URI, JWKS and short-lived signed request headers; its separate bot-registration procedure applies to Cloudflare's verification program. [Signing and directory guide](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/).
2. Establish Shopify recognition of that directory. Shopify's Checkout WebMCP documentation says verification uses registered keys and instructs registering/publishing the directory **with Shopify**. The link points to the generic Storefront guidance, which does not expose a distinct self-service registration procedure in the inspected text. Do not treat a locally generated signature as proof the origin recognizes it, or substitute Cloudflare registration for Shopify registration. Whether an existing approved operator identity is already available must be inventoried before building another signer. [Shopify authentication guidance](https://shopify.dev/docs/agents/carts-and-checkout/checkout-webmcp#authenticate).
3. Add signing at the existing request/browser integration boundary and verify on a controlled receiver that actual HTTPS navigation, relevant subrequests and redirect handling preserve the intended signature semantics. A static header reused after expiry or for a different authority is insufficient. Then make a small Militado read-only request and retain a redacted identity/result receipt. This is an implementation/proof step, not solved by successfully retrieving unsigned HTML. The precise signature components and timestamps must follow the selected protocol and provider's requirements. [Cloudflare mechanics](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/), [Shopify WBA](https://shopify.dev/docs/api/storefront/latest#identifying-bots-with-web-bot-auth).

For supported storefront actions, Shopify documents `search_catalog`, `browse_store`, `get_product` and `show_variant`. `get_product` returns variants/prices/availability; `show_variant` selects an exact or partial option combination. These provide a native route to investigate before inventing Shopify JSON scraping or click automation. Browser support is currently Chromium-based. Catalog access and public policy reading should be tested before any cart or checkout operation. [Storefront WebMCP tools](https://shopify.dev/docs/api/web-mcp).

## What this can resolve

The research question can be answered by an explicit matrix containing qualified, provisional, blocked and unsupported operations; it does not require making every source work. Missing provider access can be an evidenced negative result, with that route disabled and a named prerequisite. It would be misleading to keep cycling through browsers or to pretend a provider block is an offer absence.

The current ticket says its gate remains open while required live receipts/access authority are missing. A final coverage-classification decision can meet that gate when each mandatory family has either the required operational receipt **or an evidenced blocked/unsupported outcome**, with limits explicitly retained. This is different from deleting the family or calling it qualified. This documentation asset alone cannot establish the positive live operations; the parent owns those receipts and the final resolution.

Suggested precise resolution boundary:

> Accept this roster and five-case cohort for further design. Each operation's status is limited to the linked tested behavior or documented blocker. Blocked and unsupported routes stay disabled; provisional results are review leads, not verified deals. No completeness, repeated freshness, archival licence or UK best-price claim is accepted. The following provider/identity prerequisites remain required before those operations can be enabled: [name the relevant rows]. Exact-offer evidence, history retention, UK costing and operating cadence retain the acceptance gates in their named downstream tickets.

That resolves a research decision without claiming universal access. If the agreed product requires a currently blocked operation to work before any downstream design proceeds, that is a distinct named dependency and must remain blocked. No browser installation or user approval can manufacture provider recognition or rights. This asset changes no ticket status.
